- 2026-07-22 — Senior quality pass (review + README + benchmarks + hygiene). Two real defects found and fixed, each with a test that fails before the fix:
  1. **Rollup aggregation depended on the Postgres session TimeZone.** `date_trunc('hour', ts)` and the `${day}::date` day bounds are both evaluated in the session zone, so on any non-UTC server the daily window shifted off the UTC day, and on a fractional-offset zone (e.g. +05:30) a single UTC hour split across two hourly buckets. Verified against Postgres before fixing. Fixed with `date_trunc('hour', ts, 'UTC')` and explicit `timestamptz` day bounds, plus `connection: { TimeZone: "UTC" }` on the pool as defence in depth. Test: `tests/integration/rollupTimezone.test.ts` runs the real recompute functions over an Asia/Kolkata connection.
  2. **`event_raw` had no ts-leading index.** The rollup recomputes and the retention prune filter on `ts` alone across all sites, which `event_raw_site_ts_idx (site_id, ts)` cannot serve, so every hourly bucket sequentially scanned the whole raw table (up to 78 times per run). Added `event_raw_ts_idx (ts)` via migration `0001_event_raw_ts_idx`. Measured on 1M time-ordered events: full rollup 22.49s -> 12.68s; single-bucket plan parallel seq scan 120ms -> index scan 64ms. Test: `tests/integration/schemaIndexes.test.ts` asserts a ts-leading index exists (fails with only 0000 applied).

- 2026-07-22 — Review verdicts on the areas that turned out to be sound, recorded so they are not re-litigated: read/write split (stats reads rollups only, static test guards it); salt get-or-create race (`INSERT ... ON CONFLICT DO NOTHING` then `SELECT` is race-safe; destruction deletes `< today`; no cross-day linkage); watermark/grace interaction (monotonic, half-open intervals, an hour finalizes only once it has been over >= 5 min, daily always recomputed whole from raw); ingest origin/site-id spoofing (an event is always attributed to its own sid's site and the origin must match that site's domain, so cross-site poisoning is not possible — self-inflation of a public site id is inherent to any public pixel); DNT/GPC honored in both snippet and endpoint; IP never persisted or logged (no column, logger rejects ip/userAgent fields, log-capture test); session HMAC uses `timingSafeEqual` on equal-length buffers plus an expiry check; no SQL injection (every interpolation is a parameterized tagged-template bind, no string concatenation of user input).

## Decisions log

- 2026-07-18 — Postgres over SQLite: ingestion writes concurrently with the rollup job's recompute transactions; SQLite's single-writer model is the wrong shape. Trade-off (one extra service) accepted; docker-compose proposed for dev.
- 2026-07-18 — Drizzle over Prisma: the core of the app is hand-written aggregation SQL; Drizzle stays close to SQL and its migrations are reviewable SQL files. Neither reference project has a DB, so no convention existed to follow.
- 2026-07-18 — Rollups are recompute-and-overwrite (upsert from raw per bucket), never incremented. This single choice provides idempotency, replay safety, and catch-up after missed cron runs.
- 2026-07-18 — Daily salt destruction (delete all salts before today) is the cross-day unlinkability guarantee; past rollup recomputation uses materialized hashes and never needs old salts.
- 2026-07-18 — Aggregation is triggered by cron hitting a bearer-protected route rather than a standalone script: one deployable, one env/DB bootstrap, works with any scheduler.
- 2026-07-18 — No auth or validation libraries: node:crypto (scrypt + HMAC cookie) and hand-rolled validators cover the single-admin, three-field-payload reality. Proposed dependency list is only drizzle-orm, drizzle-kit, postgres, uplot, maxmind — all pending owner approval.
- 2026-07-18 — Multi-day "visitors" is the sum of daily uniques and is labeled as such in the UI; exact cross-day dedup is impossible by design and that is the point.
- 2026-07-18 — Dev Postgres runs via `docker run postgres:16` published on localhost:5432; `.env` (gitignored) points DATABASE_URL there. Separate `pulse_test` database for integration tests via TEST_DATABASE_URL; `tests/setup.ts` redirects the app DB client to it so tests never touch dev data.
- 2026-07-18 — Env-loading uses Node's built-in `process.loadEnvFile`/`--env-file` (no dotenv dependency). `drizzle.config.ts` loads .env only when DATABASE_URL is unset so an explicit env var can target the test DB.
- 2026-07-18 — Build environment cannot run the Next.js server: `next dev`/`next start` (next-server) is killed with signal 16 on startup in this sandbox, while a plain Node HTTP server and outbound Postgres both work. Verification therefore uses `next build` for compile/render coverage and direct route-handler invocation (as prescribed in docs/testing.md) for API/pipeline coverage; live-server HTTP smoke and Playwright e2e are logged as manual steps to run in a normal environment.
- 2026-07-18 — visitor hash concatenation uses null-byte separators between fields (salt/site/ip/ua) to keep boundaries unambiguous; still sha256 truncated to 128 bits (32 hex).
- 2026-07-18 — Rollup SQL binds all timestamps as ISO text with an explicit `::timestamptz` cast (never a raw JS Date) so the hand-written postgres.js queries survive cross-realm module loading in the test runner; drizzle inserts are unaffected. Vitest runs test files sequentially (`fileParallelism:false`) because integration tests share one Postgres database and truncate between cases.
- 2026-07-18 — Rollup route validates the bearer token with `timingSafeEqual`. Collect `DNT`/bot drops return 202 (accepted, nothing stored) so probes cannot distinguish a tracked vs untracked site.
- 2026-07-18 — Middleware runs on the Edge runtime, which lacks node:crypto, so it does a presence-only cookie gate (redirect pages to /login, 401 guarded APIs). Authoritative HMAC signature+expiry verification happens in every guarded route handler and server component (`readRequestSession`/`getServerSession`), so a forged cookie passes the gate but fails at the data layer. `lib/auth/constants.ts` holds the crypto-free cookie constants shared by Edge middleware and Node code.
- 2026-07-18 — Next.js route files may only export HTTP-method handlers + a few config fields, so shared helpers (e.g. `serializeSite`) live in `lib/`, not in the route module. The snippet is async, so `document.currentScript` is null at run time; it finds its own tag via `document.querySelector("script[data-site]")` and derives the collect endpoint with `new URL("/api/collect", script.src)`.
- 2026-07-22 — Playwright e2e is deliberately excluded from CI: it needs a browser download plus a production server on top of Postgres, which is slow and the historical source of flakiness here (the browser-cache lock contention noted below). The pipeline integration test already covers ingest -> rollup -> stats in CI, so e2e stays a local/manual step, documented in the README and in a comment at the top of the workflow.

- 2026-07-23 — Custom events use a SEPARATE `custom_event_raw` table, not a `name` column on `event_raw`. Reason: every existing pageview rollup does `count(*)`/`count(DISTINCT visitor_hash)` over `event_raw` assuming every row is a pageview; adding events into that table would force a `WHERE`-filter edit into all five proven recompute statements and risk regressing them. A second raw table keeps the pageview path pristine and mirrors the existing write-path shape.
- 2026-07-23 — Custom events are counts-only, so `custom_event_raw` stores no visitor hash and the collect handler never reads the IP for an event. This is stricter privacy than pageviews (no personal-data derivation at all) and is the whole v1 scope — arbitrary properties stay a non-goal.
- 2026-07-23 — Custom events roll up to a DAILY table only (`rollup_custom_event_daily`), matching the existing breakdown tables; "today" works because the current day's rollup is recomputed (partial) on every run. No hourly custom rollup exists because there is no hourly custom-events panel (YAGNI).
- 2026-07-23 — The rollup summary's `rawPruned` now totals both raw tables (pageview + custom event) rather than gaining a new field, keeping the documented `/api/jobs/rollup` response shape stable; both tables share the same 72-hour retention window so a single figure is honest. Documented in api-contracts.md.

- 2026-07-18 — e2e runs in this environment: `next start` (via Playwright's webServer) starts fine; the earlier standalone next-server kills were caused by two concurrent `playwright install` processes contending on the browser cache lock, not by the server. After serializing the browser install, `npm run test:e2e` passes 2/2.
